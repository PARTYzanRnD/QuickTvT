# Plan: Winner Tracking, Defending Side Restriction & PolyZone Faction Replication

## Overview

Two interconnected features:
1. **PolyZone `m_aVisibleForFactions` replication** — `PS_PolyZone` is a `ScriptComponent` with no network replication. Directly modifying `m_aVisibleForFactions` on the server does NOT propagate to clients. Need to add RPC-based replication.
2. **Winner tracking & defending side restriction** — Store winners via JsonApiStruct, restrict defending side (fewer slots) character selection to previous round winners only.

---

## Part A: PolyZone Faction Visibility Replication

### Problem

In `pzn_SCR_CampaignBuildingProviderComponent.c` (`PodvalTvTMissions`), `Updatestupidzones()` does:
```c
PS_PolyZone polyzone2zone = PS_PolyZone.Cast(polyzone.FindComponent(PS_PolyZone));
polyzone2zone.m_aVisibleForFactions.Insert(flagFactionKey);
polyzone2zone.m_aVisibleForFactions.Insert(flagFactionKey2);
```

This only modifies the server-side array. Clients never receive these changes because `PS_PolyZone` is a `ScriptComponent` with **no RplSave/RplLoad, no [RplProp], no RPC** — it's a purely local component. The `IsCurrentVisibility()` method reads `m_aVisibleForFactions` locally, so each client evaluates it against the **original prefab values** (typically empty or default), never seeing the server's runtime Insert.

### Solution: Modded PS_PolyZone with RPC

Use the same pattern as `PS_ManualMarker` (also in PSCore): **server-authoritative setter + `[RplRpc(Broadcast)]`**.

Since `PS_PolyZone` is a `ScriptComponent`, not a `GenericEntity`, it cannot use `RplSave`/`RplLoad` (those are for RplComponent entities). RPC is the correct approach for components.

#### A1: New file `scripts/game/lib/QTvT_M_PolyZone.c`

```c
modded class PS_PolyZone
{
    // Server-authoritative setter for faction visibility
    void SetVisibleForFaction(FactionKey factionKey, bool visible)
    {
        if (!Replication.IsServer()) return;
        Rpc(RPC_SetVisibleForFaction, factionKey, visible);
        RPC_SetVisibleForFaction(factionKey, visible); // also apply on server locally
    }

    [RplRpc(RplChannel.Reliable, RplRcver.Broadcast)]
    void RPC_SetVisibleForFaction(FactionKey factionKey, bool visible)
    {
        if (visible)
        {
            if (!m_aVisibleForFactions.Contains(factionKey))
                m_aVisibleForFactions.Insert(factionKey);
        }
        else
        {
            m_aVisibleForFactions.RemoveItem(factionKey);
        }
        // Refresh map widget if open
        if (m_MapEntity && m_MapEntity.IsOpen())
        {
            if (IsCurrentVisibility())
            {
                if (!m_wCanvasWidget) CreateMapWidget(m_MapEntity.GetMapConfig());
            }
            else
            {
                if (m_wCanvasWidget) DeleteMapWidget(m_MapEntity.GetMapConfig());
            }
        }
    }
}
```

Key design decisions:
- **`SetVisibleForFaction(key, visible)`** — follows the exact same signature pattern as `PS_ManualMarker.SetVisibleForFaction()` which already exists in PSCore
- **Calls `Rpc()` + local application** — standard Enforce pattern: server calls RPC for clients AND applies locally (since Broadcast excludes server on dedicated)
- **Map widget refresh** — after modifying visibility, check if the map widget needs to be created/deleted, matching the same refresh logic in `PS_ManualMarker.RPC_SetVisibleForFaction_ByKey()`
- **No RplSave/RplLoad** — `PS_PolyZone` extends `ScriptComponent`, not an entity with `RplComponent`. RPC handles JIP clients who connect after the change because `OnGameStateChanged` (in `GUB_RandomizeMissionComponent`) fires on BRIEFING state transition, which will re-apply the faction visibility. If JIP before BRIEFING, the PolyZone starts with prefab defaults (empty visibility = visible to all, or whatever was set in WB), which is acceptable.

#### A2: Update PodvalTvTMissions to use the new setter

In `pzn_SCR_CampaignBuildingProviderComponent.c`, replace:
```c
polyzone2zone.m_aVisibleForFactions.Insert(flagFactionKey);
polyzone2zone.m_aVisibleForFactions.Insert(flagFactionKey2);
```
With:
```c
polyzone2zone.SetVisibleForFaction(flagFactionKey, true);
polyzone2zone.SetVisibleForFaction(flagFactionKey2, true);
```

This is a **separate repo** (`PodvalTvTMissions`). The change is minimal — just swap direct array mutation for the new method call.

### Why not RplSave/RplLoad?

`PS_PolyZone` extends `ScriptComponent`, not `GenericEntity`. Components don't have `RplSave`/`RplLoad` unless they use `RplComponent` as a parent entity's replication. The RPC approach is simpler and matches the existing `PS_ManualMarker` pattern perfectly. It also avoids the complexity of comma-delimited string serialization for JIP (which ManuaMarker uses but is fragile).

### Why not [RplProp] on the array?

`[RplProp]` on `ref array<FactionKey>` would require the array to be a replicated property, but Enforce script replication of dynamic arrays is unreliable and doesn't handle Insert/Remove well after initial replication. RPC is the established pattern in this codebase.

## Part B: Winner Tracking & Defending Side Restriction

### B1: Create Winner Storage — `scripts/game/lib/QTvT_WinnerStore.c` (NEW)

```
class QTvT_WinnerEntry: JsonApiStruct
  - string m_sPlayerUID
  - string m_sPlayerName
  - RegV both fields

class QTvT_WinnerList: JsonApiStruct
  - ref array<ref QTvT_WinnerEntry> m_aWinners
  - string m_sWinningFaction
  - RegV both fields
  - SaveToProfile() — SCR_JsonSaveContext to "$profile:QuickTvT_Winners.json"
  - static LoadFromProfile() — SCR_JsonLoadContext from "$profile:QuickTvT_Winners.json"
  - ContainsUID(string uid) — iterates m_aWinners, returns true if found
  - Clear() — clears m_aWinners and m_sWinningFaction
```

### B2: Add Defending Faction & Winner Capture — `PS_GameModeQuickTvT.c` (MODIFY)

**New member variables:**
- `FactionKey m_sDefendingFaction` — cached defending faction (fewest slots)
- `ref QTvT_WinnerList m_WinnerList` — in-memory winner list for current session

**New method `ComputeDefendingFaction()`:**
1. Get `PS_PlayableManager` instance
2. Get all playables sorted
3. Count slots per faction
4. Return faction key with minimum slot count
5. Store in `m_sDefendingFaction`

**New method `GetDefendingFaction()`:**
- Returns `m_sDefendingFaction`

**New method `GetWinnerList()`:**
- Returns `m_WinnerList`

**Modify `CheckAlive()`:**
When `m_OnOnlyOneFactionAlive.Invoke(checkFaction)` fires:
1. Create new `QTvT_WinnerList`
2. Iterate playables, find alive ones belonging to `checkFaction`
3. For each alive playable with `playerId > 0`:
   - Get UID: `m_PlayerManager.GetPlayerUID(playerId)`
   - Get name: `m_PlayerManager.GetPlayerName(playerId)`
   - Insert `QTvT_WinnerEntry` into winner list
4. Set `m_sWinningFaction = checkFaction`
5. Store in `m_WinnerList`
6. `m_WinnerList.SaveToProfile()`

**Modify `OnGameStateChanged()`:**
- SLOTSELECTION: Call `ComputeDefendingFaction()`, load `m_WinnerList` from profile if null
- PREGAME: Clear `m_WinnerList` (new mission rotation, no carry-over)

### B3: Restrict Defending Side Selection — `QTvT_M_CharacterSelector.c` (MODIFY)

In `OnClicked()`, add a check **after** the existing faction balance check and **before** the actual slot assignment:

1. Get `PS_GameModeQuickTvT` instance
2. If current game state is SLOTSELECTION or BRIEFING:
   - Get defending faction key
   - If `m_sFactionKey == defendingFaction`:
     - Get current player UID via `PlayerManager.GetPlayerUID(playerId)`
     - If UID is NOT in `gameMode.GetWinnerList()`:
       - If player is NOT admin (`PS_PlayersHelper.IsAdminOrServer()`):
         - Send chat message "Only previous round winners can select the defending side"
         - Show preview only + fail sound, return

### B4: Edge Cases

- **First round**: No `QuickTvT_Winners.json` exists → `LoadFromProfile()` returns null/empty → `ContainsUID()` always false → `m_WinnerList` is null → skip restriction (anyone can pick any side)
- **Timer expiry**: No `CheckAlive()` winner determined → `m_WinnerList` stays null from previous clear or stays from previous round (design choice: **clear on DEBRIEFING if no winner was set**)
- **Admin bypass**: `PS_PlayersHelper.IsAdminOrServer()` check allows admins to pick any side
- **Equal slot counts**: If all factions have equal slots, `ComputeDefendingFaction()` returns first alphabetically or empty — no restriction applied when there's no clear defending side (all factions have same slot count)

## Open Questions

1. **Timer expiry with no winner**: Should we clear the winner list (no restriction next round) or determine winner by most alive playables/players? My recommendation: **clear the list** — if nobody eliminated the other side, nobody "won".
2. **Equal slot counts**: If both factions have the same number of slots, should there be a defending side at all? My recommendation: **no restriction** — the defending side concept only applies when one faction has fewer slots.
